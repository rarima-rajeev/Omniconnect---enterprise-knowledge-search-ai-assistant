## Summary

Severity P1. On October 12 at 04:15 UTC the primary node of Postgres-RDS-Cluster-01 in us-east-1, `rds-prod-primary-a`, suffered a kernel panic caused by ECC memory degradation on the underlying hypervisor host. RDS Multi-AZ failover promoted the standby `rds-prod-replica-b` to primary. Total incident duration was 42 minutes.

## Timeline (UTC)

- 04:15 Primary stops responding; CloudWatch alarm `rds-primary-heartbeat` fires.
- 04:16 Multi-AZ failover starts automatically.
- 04:17 DNS endpoint switches to `rds-prod-replica-b`. Failover itself took 71 seconds.
- 04:17-04:24 Application connection pools (PgBouncer) keep stale connections to the old primary; gateway error rate peaks at 18%.
- 04:24 On-call engineer manually drains PgBouncer pools; error rate returns to normal.
- 04:24-04:57 Elevated latency while caches warm and read replicas re-sync to the new primary.
- 04:57 Incident resolved.

## Root cause

The hardware fault was outside our control, but the extended impact came from PgBouncer's `server_check_delay` being set to 300 seconds, so pools did not detect the dead primary quickly. Pool drain completed in 180 seconds once triggered manually.

## Data integrity

WAL replay on the promoted node was verified with 0% data loss. Synchronous replication meant no committed transactions were lost.

## Action items

1. Reduce PgBouncer `server_check_delay` to 10 seconds and enable `server_fast_close` (owner: Alex Rivera, due Oct 31).
2. Add an automated pool drain triggered by the RDS failover event (owner: SRE platform, due Nov 15).
3. Run a monthly game-day failover drill in staging (owner: SRE, starting November).
4. Alert on connection error rate above 5% for 60 seconds (owner: Observability, due Oct 24).
