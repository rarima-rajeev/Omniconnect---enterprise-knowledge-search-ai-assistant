## When to use this runbook

Use this runbook when the `rds-primary-heartbeat` alarm fires, when the gateway error rate for database calls exceeds 5%, or when AWS reports a Multi-AZ failover event for any production cluster.

## Step 1: Confirm the failover

Check the RDS events page for the cluster. A Multi-AZ failover normally completes in 60 to 120 seconds. Confirm the writer endpoint now resolves to the former standby.

## Step 2: Drain connection pools

PgBouncer may hold stale connections to the old primary. Run `omni-ops pgbouncer drain --region <region>` from the bastion. This reconnects every pool in about three minutes. Watch the gateway error rate in the "DB health" Datadog dashboard; it should drop below 1% within five minutes.

## Step 3: Verify replicas

Check that every read replica reports replication lag under 10 seconds against the new primary. If a replica does not recover within 15 minutes, remove it from the read pool with `omni-ops replica disable <id>`.

## Step 4: Verify data integrity

Run the `wal-consistency-check` job. It compares the last committed transaction IDs before and after failover. Any gap must be escalated to the database lead immediately.

## Step 5: Communicate

Post an update on the status page within 15 minutes of the first alert, and every 30 minutes until resolved. Notify the #incident channel and page the incident commander for any P1.

## Step 6: Restore redundancy

AWS will provision a new standby automatically. Confirm it is in sync before closing the incident. If the old primary's host had a hardware fault, open an AWS support case and attach the instance ID.

## After the incident

Write a post-mortem within five business days using the standard template, including a timeline, the root cause, the customer impact and action items with owners.
